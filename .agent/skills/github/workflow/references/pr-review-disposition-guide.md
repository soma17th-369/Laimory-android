# PR 리뷰 코멘트 판단 기준

리뷰 코멘트는 빠르게 처리하되, 각 판단은 설명 가능해야 합니다.
사용자와 리뷰어에게 왜 그 판단을 했는지 한두 문장으로 말할 수 있어야 합니다.

## 1. 판단 순서

1. 리뷰어가 현재 코드 동작을 사실대로 이해했는가?
   - 아니면: 사유 있는 거절
   - 맞으면: 다음 단계
2. 제품 정책, UX, 팀 컨벤션처럼 작성자 판단이 필요한가?
   - 맞으면: 사용자 확인 필요
   - 아니면: 다음 단계
3. 제안 변경이 리뷰어가 보지 못한 다른 코드나 호출부를 깨뜨리는가?
   - 맞으면: 사유 있는 거절
   - 아니면: 다음 단계
4. 이 PR 범위 안에서 처리해야 하는가?
   - 범위 밖이지만 유효하면: 보류
   - 범위 안이면: 다음 단계
5. 제안 그대로 적용해도 되는가?
   - 그대로 가능하면: 수용
   - 조정이 필요하면: 수정 수용

## 2. 처리 방침

| 방침 | 기준 |
|---|---|
| 수용 | 리뷰어 지적이 맞고, 제안 변경이 그대로 적절함 |
| 수정 수용 | 방향은 맞지만 이름, 범위, 구현 방식 조정이 필요함 |
| 사유 있는 거절 | 리뷰어 전제가 틀렸거나 변경 시 다른 문제가 생김 |
| 보류 | 유효한 지적이지만 현재 PR 범위를 벗어남 |
| 사용자 확인 필요 | 제품/정책/컨벤션/큰 변경처럼 사용자 판단이 필요함 |

## 3. 보수적 선택 기준

- 수용과 보류가 모두 가능하면, 작은 변경은 수용합니다.
- 거절과 사용자 확인이 모두 가능하면, 사용자 확인을 우선합니다.
- 제안을 조금이라도 조정했다면 수용이 아니라 수정 수용으로 답변합니다.

## 4. 피해야 할 패턴

- 코드는 고쳤지만 리뷰어에게 답변하지 않는 것
- 충분한 근거 없이 길게 반박하는 것
- 작은 nit이라는 이유로 컨벤션 변경을 무비판적으로 대량 반영하는 것
- 현재 파일을 읽지 않고 diff hunk만 보고 판단하는 것
