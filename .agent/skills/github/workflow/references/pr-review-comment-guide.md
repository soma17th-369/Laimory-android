# PR 리뷰 코멘트 처리 가이드

PR에 남은 unresolved 리뷰 코멘트를 하나씩 확인하고, 실제 코드 기준으로 수용/수정 수용/거절/보류/사용자 확인 필요 여부를 판단합니다.
목표는 리뷰어의 모든 코멘트에 명확한 답변을 남기고, 필요한 변경을 코드에 반영하는 것입니다.

## 1. 사용 시점

- 사용자가 PR 리뷰 코멘트 처리를 요청할 때
- PR URL 또는 번호를 주고 피드백 반영을 요청할 때
- 리뷰 코멘트를 붙여넣고 어떻게 처리할지 정리해 달라고 할 때

초기 PR 설명 작성, 첫 코드 리뷰, 머지 작업에는 이 흐름을 사용하지 않습니다.

## 2. 처리 흐름

### 2.1 PR 식별

- PR URL이 있으면 owner, repo, PR 번호를 파싱합니다.
- 번호만 있으면 현재 저장소를 기준으로 확인합니다.
- 정보가 없으면 `gh pr status`로 현재 브랜치 또는 작성자 PR을 확인하고 사용자에게 대상 PR을 확인받습니다.

### 2.2 unresolved thread 수집

`gh-command-guide.md`의 GraphQL 쿼리로 `isResolved == false`인 review thread를 수집합니다.
처리 단위는 개별 댓글이 아니라 thread입니다.

### 2.3 계획 먼저 공유

코드를 수정하기 전에 발견한 thread 목록과 각 요청 내용을 짧게 정리해서 사용자에게 확인받습니다.

```text
1. app/src/.../TimelineScreen.kt:42 - 상태 분기 네이밍 개선 요청
2. core/data/.../Mapper.kt:18 - null 처리 누락 가능성 지적
3. README.md - 실행 예시 추가 요청
```

### 2.4 thread별 판단

각 thread마다 아래 순서로 처리합니다.

1. 현재 파일을 직접 읽습니다. diff hunk만 믿지 않습니다.
2. 코멘트의 의도가 현재 코드에도 유효한지 확인합니다.
3. 처리 방침을 결정합니다.
4. 수용하는 경우 코드를 수정하고 관련 검증을 실행합니다.
5. thread에 짧고 구체적으로 답변합니다.
6. 팀 규칙상 적절한 경우에만 thread를 resolve합니다.

## 3. 답변 템플릿

### 3.1 수용

```text
반영했습니다. `parseToken` 네이밍을 `parseAuthToken`으로 변경하고 호출부도 함께 수정했습니다.
```

### 3.2 수정 수용

```text
방향에 동의합니다. 다만 제안해주신 이름은 기존 심볼과 겹쳐 `parseAuthToken`으로 조정해 반영했습니다.
```

### 3.3 사유 있는 거절

```text
확인해보니 현재 구조를 유지하는 편이 맞다고 판단했습니다. 이 함수명은 같은 패키지의 `extractSession`, `extractRefresh` 컨벤션과 맞추기 위한 의도입니다.
```

### 3.4 보류

```text
좋은 지적입니다. 다만 이 PR 범위를 넘어서는 변경이라 후속 이슈로 분리하겠습니다.
```

### 3.5 사용자 확인 필요

```text
의도를 정확히 맞추고 싶습니다. 재시도 횟수를 줄이는 방향인지, 재시도 자체를 제거하는 방향인지 확인 부탁드립니다.
```

## 4. 주의사항

- 오래된 diff의 코멘트일 수 있으므로 현재 파일 기준으로 다시 확인합니다.
- bot 코멘트도 무조건 무시하지 말고 실제 유효성을 판단합니다.
- 실질적인 논쟁 여지가 있으면 작성자가 임의로 resolve하지 않습니다.
- 리뷰어에게 답변 없이 코드만 수정하지 않습니다.
- 큰 변경으로 번질 경우 사용자에게 먼저 확인합니다.
