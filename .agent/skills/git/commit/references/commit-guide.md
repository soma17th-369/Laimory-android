# 커밋 가이드

커밋은 변경 이력을 추적하고 리뷰 범위를 이해하기 위한 최소 단위입니다.

## 1. 커밋 메시지 형식

```text
<type>: <summary> (#<issue-number>)
```

예시:

```text
feat: 타임라인 위치 표시 구현 (#12)
fix: 날짜 정렬 오류 수정 (#34)
chore: KtLint 세팅 (#5)
refactor: Repository 레이어 분리 (#18)
```

## 2. 커밋 타입

| Type | 기준 |
|---|---|
| `feat` | 사용자에게 보이는 기능 추가 또는 기능 단위 구현 |
| `fix` | 버그 수정, 예외 처리, 비정상 동작 수정 |
| `refactor` | 동작 변경 없이 구조, 네이밍, 책임 분리 개선 |
| `test` | 테스트 추가, 수정, 테스트 유틸 정리 |
| `docs` | 문서 추가 또는 수정 |
| `chore` | 빌드, 설정, 의존성, 포맷팅, 운영성 작업 |

## 3. 커밋 단위

- 하나의 커밋은 하나의 논리적 변경만 포함합니다.
- 커밋 메시지 한 줄로 변경 의도를 설명할 수 있어야 합니다.
- 기능 구현, 리팩터링, 테스트, 문서 수정은 가능하면 분리합니다.
- 같은 이유로 수정된 파일들은 함께 커밋할 수 있습니다.
- 빌드가 깨지는 중간 상태는 커밋하지 않습니다.
- 단순 포맷팅은 기능 변경과 섞지 않습니다.
- 리뷰 반영 커밋은 댓글 단위보다 변경 의도 단위로 묶습니다.

## 4. 좋은 커밋 단위 예시

```text
feat: 타임라인 목록 상태 모델 추가 (#12)
feat: 타임라인 empty/loading 상태 처리 (#12)
test: 타임라인 ViewModel 상태 전이 테스트 추가 (#12)
fix: 타임라인 날짜 정렬 오류 수정 (#34)
```

## 5. 피해야 할 커밋

```text
feat: 타임라인 구현 (#12)
fix: 이것저것 수정 (#34)
chore: 리뷰 반영 (#12)
```

- 범위가 넓어 리뷰 기준을 알기 어려운 커밋
- 기능 변경과 대량 포맷팅이 섞인 커밋
- 여러 이슈의 변경이 한 커밋에 섞인 커밋
- 메시지만 봐서는 변경 의도를 알 수 없는 커밋

## 6. 커밋 메시지의 `@` 표기

커밋 메시지는 GitHub에서 링크나 멘션처럼 처리될 수 있으므로 코드 어노테이션을 설명할 때도 가능하면 `@` 문자를 직접 쓰지 않습니다.

권장:

```text
docs: Hilt Provides 어노테이션 규칙 추가 (#68)
docs: Compose Composable 계층 규칙 정리 (#68)
docs: `@Provides` 어노테이션 규칙 추가 (#68)
```

피함:

```text
docs: @Provides 규칙 추가 (#68)
docs: @Composable 계층 규칙 정리 (#68)
```

- 실제 사람이나 팀을 호출해야 하는 경우가 아니라면 커밋 메시지에 GitHub 멘션을 쓰지 않습니다.
- 코드 어노테이션의 정확한 표기가 꼭 필요하면 `@Provides`처럼 Markdown code span으로 감쌉니다.
- 자세한 코드 심볼 설명은 커밋 메시지보다 이슈/PR 본문에 작성합니다.

## 7. 예외 처리

- 이슈 번호가 없는 커밋은 사용자에게 이슈 생성 또는 예외 허용 여부를 확인합니다.
- 설정 초기화처럼 이슈가 과한 작업은 `chore: 프로젝트 설정 초기화`처럼 이슈 번호 없이 작성할 수 있습니다.
- 여러 이슈를 함께 처리한 경우 대표 이슈를 메시지에 쓰고, 상세 연결은 PR 본문에 정리합니다.
